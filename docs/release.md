# Release

`@treansai/agenomic-typescript` is published to npm by `.github/workflows/release.yml`.
The workflow fires on a `v*` tag, builds and tests the tree, refuses to go on when the
tag and `package.json` disagree on the version, then publishes through npm trusted
publishing (OIDC). No npm token is stored in the repository.

## One-time bootstrap

npm cannot attach a trusted publisher to a package that does not exist yet, so the first
version is published by hand. Everything after it goes through the workflow.

1. Merge the release branch into `main` and check out that commit. Every step below
   assumes it: the tag pushed at the end must point at a commit that already contains
   `.github/workflows/release.yml`, or the push event finds no workflow to run, and the
   release job refuses a tag that is not reachable from `main`.

2. Authenticate against npm as a member of the `treansai` organization:

   ```bash
   npm login
   npm whoami
   ```

3. Enable two-factor authentication on that account. This is not optional and it is not
   only about the publish: `npm trust` in step 5 states "Two-factor authentication must be
   enabled at the account level", and a granular access token with bypass 2FA is rejected
   by the trust commands and is being restricted by npm for direct publishing.

   ```bash
   npm profile get          # "two-factor auth" must not read "disabled"
   npm profile enable-2fa auth-and-writes
   ```

   Without it, `npm publish` answers `403 Forbidden ... Two-factor authentication or
   granular access token with bypass 2fa enabled is required to publish packages`.

4. Build and publish `0.1.1` from a clean tree. `auth-and-writes` asks for a one time
   password on the publish itself, so pass it on the command or answer the prompt:

   ```bash
   corepack pnpm@10.0.0 install --frozen-lockfile
   corepack pnpm@10.0.0 run build
   corepack pnpm@10.0.0 run test
   npm publish --access public --otp=123456
   ```

   `publishConfig.access` is already `public`, so the scoped package is not published
   private. `--access public` is kept on the command as a second guard.

   This one publish is not attested: provenance is generated by the workflow, so `0.1.1`
   is the only version on the registry without it. `0.1.2` onward are attested.

5. Configure the trusted publisher on npmjs.com:
   Packages -> `@treansai/agenomic-typescript` -> Settings -> Trusted publishing ->
   GitHub Actions, with

   | Field | Value |
   | --- | --- |
   | Organization or user | `treansai` |
   | Repository | `agenomic-typescript` |
   | Workflow filename | `release.yml` |
   | Environment | `npm` |

   The equivalent from the CLI is `npm trust github`, which needs npm 11.15.0 or later;
   the website works on any version.

6. Create the `npm` environment in the GitHub repository
   (Settings -> Environments -> New environment -> `npm`). The workflow names it, and the
   trusted publisher checks it. Add required reviewers there if a release should be gated
   by a human.

7. Revoke the token or session used for step 4. It existed only to cover the first
   publish.

8. Move the existing `v0.1.1` tag onto the merged release commit and push it:

   ```bash
   git tag -f v0.1.1
   git push --force origin v0.1.1
   ```

   The tag currently sits on the pre-release commit, which carries no workflow and the
   unscoped `0.1.0` package. Moving it fires the pipeline for the first time. `0.1.1` is
   already on the registry by then, so the publish step reports it and skips; the run
   still produces the GitHub release for `v0.1.1`. That skip is the only time it happens
   by design.

## Every release after that

1. Bump `version` in `package.json` on `main`, commit, merge.
2. Tag the release commit and push the tag:

   ```bash
   git tag v0.1.2
   git push origin v0.1.2
   ```

The workflow then publishes the package with provenance and opens a GitHub release
carrying the same tarball and generated notes.

A tag carrying a prerelease suffix (`v0.2.0-rc.1`) is published under the `next` dist-tag
and the GitHub release is marked as a prerelease, so `latest` is never moved by a
release candidate.

## What the workflow will not do

- It will not publish a tag whose commit is not reachable from `main`. A `v*` tag on an
  unmerged branch fails at the first step, before any build or publish. Merge first, then
  tag the merged commit.
- It will not publish when `package.json` disagrees with the tag. Fix the version on
  `main`, then move the tag.
- It will not publish from a fork or from a branch. Only a `v*` tag triggers it.
- It will not republish a version already on the registry. Re-running a tag is safe: the
  publish step skips and the GitHub release is still produced. To ship new code, bump
  `package.json` and tag the new version; a tag that disagrees with `package.json` is
  rejected by the guard before anything is built.
