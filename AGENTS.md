# AGENTS.md

Decisions that would otherwise live in code comments. Keep entries short and factual.

## Protect

- Request helper: `tools.ts` exports `fetchJson` (transport only), `acceptJson` (2xx or typed `ToolExecutionError` from `{ error: { code, message } }`, `invalid_response` on a non JSON 2xx body) and `requestJson`. `ToolsResource.request` and every `protect.ts` method go through them so there is no untyped path; the RMP resources in `rmp.ts` keep their own local-first helper because their offline mode must not throw.
- `ToolCallResult.result` is `T | null`: 202 pending and 403 denied envelopes carry `result: null` (design section 5). `router.call` still returns `T` because pending and denied always throw; `invoke` callers must null check.
- Two 403 bodies exist on `invoke`: an invoke envelope (`{ result: null, agenomic: { record_id, ... } }`) becomes `ToolCallDenied`; a plain `{ error }` body (capability lapse, permit invalid, run not active) stays a `ToolExecutionError` with the server code. `readEnvelope` decides on the presence of `agenomic.record_id`.
- `authorizeLocal` accepts the decision on a 2xx body or on a 403 body that carries `decision` or `protect` (the gateway answers 200 local/gateway, 202 pending, 403 denied). The 403 gate tests for the presence of the key (`"decision" in body`), not for a string value: a 403 carrying `decision: null` or a number is an admission denial and used to fall through to `acceptJson` and surface as a generic `http_error`, which hid the denial from `ToolCallDenied` and from `router.calls`. Only `local`, `gateway` and `pending` are recognized; every other string, a missing field or a non string is `denied` (design section 9, no fallback).
- Pending and denied are admission outcomes, not tool outcomes: the router pushes the envelope to `router.calls` and throws regardless of `raiseOnError`. Synthesized local-path envelopes use real enum values only (`source: unrouted`, `fidelity: contract_only`, `external_state: none`) so `hasRealCalls` stays false.
- The permit is opaque to the SDK (`{ document, signature }` records) and forwarded verbatim in `report-local`; the SDK never inspects or verifies it (design D6).
- `beforeAction` receives the call identity (`ToolActionIntent`) and is awaited before any request on both paths, including the re-POST issued by `resume`; a throw aborts locally and leaves no evidence row. It cannot approve.
- `ToolsResource.client` is public `readonly` (it was `private`) so the router can poll `client.protect.approvals` without a second HTTP helper.
- `ToolActionIntent.executionPoint` is `runtime_local` whenever a local function is registered for the tool, even if the gateway later answers `gateway`: the hook sees the intended execution point before any request, not the final routing.
- Synthesized local-path envelopes set `agenomic.decision` to the outcome (`protect.outcome`, else `require_approval` for pending and `deny` for denied) so the field means the same thing as on gateway envelopes; the local authorize verb (`pending`, `denied`) lives in `LocalAuthorization.decision` only.
- `resume` runs through the same private `dispatch` as `call` with a `resume` argument (no instance flag) so concurrent calls on the same router never lose their idempotency key.
- `resume` looks the call identity up in a private map keyed by `approval_id` filled when `ToolApprovalPending` is thrown; an approval id the router never saw throws `unknown_approval` rather than guessing a body. The re-POST sends the identical body with the original `Idempotency-Key` (docs/protect/integration.md section 6: the middleware never records a 202, so the key is free to replay the cached 200 once the call executed). Statuses `approved` and `consumed` both re-issue exactly once, which is the behaviour the Python SDK also implements: a consumed approval already executed, so the replay recovers the stored result, and a 409 on that replay throws `ToolExecutionError("conflict", ..., 409)` rather than a denial that would suggest nothing ran. `pending` polls until `timeoutMs` (elapsed time is checked before sleeping so `timeoutMs: 0` cannot loop); `rejected`, `expired` and unknown strings throw `ToolCallDenied` with that status as `code` (fail closed).
- The consumed recovery contract is verified against a real gateway, not only against an HTTP fixture: `examples/protect-consumed-recovery.ts` is the manual harness (closure criterion 3 of the 2026-09-15 Protect campaign), run with the built bundle, and `examples/11_protect_consumed_recovery.py` in agenomic-python is its twin asserting the same contract so a divergence fails an assertion on one side. Observed on a gateway with Postgres and two user owned API keys: on the gateway executed path (`invoke`, where the SDK sends the `Idempotency-Key` derived from run, repetition and logical call id) a resume over a consumed approval answers HTTP 200 and replays the stored result with no second effect; on the runtime local path (`local/authorize`, which carries no idempotency key) the same resume answers HTTP 409 and throws `ToolExecutionError("conflict", ..., 409)`. Both branches of the contract are real and path dependent, not credential dependent, and both SDKs produce them identically. Keep both; narrowing `resume` to one branch would break the other execution point.
- `resume` claims the approval in a `resuming` set before its first `await` and releases it in a `finally`, then deletes its pending map entry before re-issuing. The deletion alone was not enough: two concurrent resumes of the same approval both read the map entry before either reached the deletion after the polling loop, both re-POSTed, and on the runtime local path, which carries no idempotency key, that executed the local function twice. A second resume while one is in flight now throws `ToolExecutionError("resume_in_flight")`; a resume that timed out has released its claim, so retrying after a timeout still works. Calling `resume` twice in sequence still ends in `unknown_approval`. The consumed path is reachable only from a second holder of the same identity, which the harness builds by having two routers issue the identical `logicalCallId` and both receive the same 202 and approval id. This is deliberate: a router must not invent an identity it never held.
- The pending map stores a deep snapshot of the arguments (`snapshotArgs`, `structuredClone` with a JSON round trip fallback). The identity kept the caller's object by reference, so mutating the arguments after the 202 made `resume` send a different payload under the logical call id and idempotency key that were approved: the replay would no longer be the approved request.
- An empty 2xx body is `invalid_response`, not `{}`. `fetchJson` leaves `parsed` undefined when the text is empty, so `acceptJson` refuses it like any other non JSON 2xx body. Turning it into an empty object let exported `requestJson` and the less strictly validated tool methods accept a response that carried no JSON at all. `benchmarks.ts` keeps its own 204 handling and is unaffected.
- `protect.ts` subclasses the RMP `ProtectResource` so `alerts`, `actionPlan`, `recommendations` and `notify` keep their local-first behaviour; `rmp.ts` exposes `client` as `protected` for that reason. `index.ts` exports the subclass under the single public name `ProtectResource`.
- Path segments in `protect.ts` are `encodeURIComponent`-encoded like `rmp.ts`; `policies.*` take `(policyId, version)` and build `policy_id@version` (`crm%402.0.0`), the format `handlers_policies.rs` splits on the first `@`.
- Wire mirrors in `protect.ts` follow `crates/agenomic-api-types/src/lib.rs` (PolicySummary, PolicyDetailResponse, SimulateResponse, PolicyDiffResponse, PolicyBinding, ProtectDecisionDto, ProtectApproval, ProtectRestriction, KillSwitchResponse, OverlayResponse, CatalogResponse, CoverageResponse, ProtectMetricsSummary) and `agenomic-policy/src/intent.rs` (`ProtectDecisionDocument` mirrors `Decision`, `ProtectDecision` mirrors `InvocationDecision`). Uuids and timestamps are strings; enums whose Rust side is a plain `String` (`scope_kind`, binding `status`, restriction `kind`) stay `string` on read and are literal unions on the write side only. Single-record responses are read bare, as the gateway sends them (`record(res, "id", ...)`, `"text"` for the overlay), and an enveloped body is an `invalid_response`: accepting both hid a wire mismatch. The three policy transitions (register, release, deprecate) are the exception, answering `PolicyResponse { policy }`, so they go through `policyRecord(res)` and return a typed `PolicyRecord`. List responses require the documented array key and raise `invalid_response` when it is absent, so an empty list and a shape mismatch stay distinct. `decisions.list` is the one paginated read and returns `{ decisions, next_cursor? }`; `policies.register` also accepts the YAML or JSON text, sent as `{ document_text }`; `bindings.list` carries the `status` filter.
- OpenAI overlay: `applyOverlay` is a pure function returning the same object when the overlay is already present (`messages[0]` is the system overlay, or `instructions` equals or starts with the overlay text followed by a blank line), so double instrumentation and retries are idempotent and the caller's request object is never mutated. For `responses.create` the recorded `model_call.input` becomes `{ instructions, input }` whenever `instructions` is present, otherwise `input`, so the trace reflects the injected request.

## Release

- The npm package is `@treansai/agenomic-typescript`; the SDK identity string is not. `SDK_METADATA.name` in `utils.ts` and the `sdk` default in `benchmarks.ts` stay `"agenomic-typescript"` because that value is a protocol constant the cloud matches on (`agenomic-cloud/crates/agenomic-onboarding/src/enroll.rs`, `AgenomicTypescript => "agenomic-typescript"`), paired with `agenomic-python`. Scoping the registry name must not move the wire value.
- `build` runs `tsup` before `typecheck`, not after. `examples/protect-consumed-recovery.ts` imports from `../dist/index.js` (deliberately: it is the harness that runs against the built bundle) and `tsconfig.json` includes `examples/**/*.ts`, so `tsc --noEmit` on a checkout with no `dist` fails with 21 unresolved-member errors. The old order made `pnpm build` impossible from a clean clone, which is exactly what CI has.
- Publishing goes through `npm publish`, not `pnpm publish`: OIDC trusted publishing landed in pnpm 10.17 and `packageManager` pins 10.0.0. The workflow upgrades the npm CLI only when the runner image ships one below 11.5.1, the version that added trusted publishing.
- The release job packs with `npm pack` and publishes the resulting tarball rather than the working directory, so the artifact attached to the GitHub release is byte-for-byte the one on the registry. That holds from 0.1.2 onward: 0.1.1 is the hand-published bootstrap, so its registry copy carries no provenance and is not the tarball its GitHub release attaches.
- The tag trigger is not the authorization. `on: push: tags` matches a name, not a history, so a `v*` tag on any unmerged branch would otherwise check out that commit and publish it under the package name, with review and branch protection bypassed. The job fetches `main` and refuses unless the checked out commit is reachable from it, which is why checkout runs at `fetch-depth: 0`. The ancestry test uses `git rev-parse HEAD` rather than `GITHUB_SHA` so it reads the same for a lightweight and an annotated tag.
- No npm token exists in the repository. `id-token: write` plus the `npm` environment is the whole credential; the bootstrap that had to precede it is in `docs/release.md`.
- `npm publish` is handed `./artifacts/<name>.tgz`, never `artifacts/<name>.tgz`. npm-package-arg only treats a spec as a file when it starts with `.`, `/`, `~/`, a drive letter or `file:`; a bare `a/b.tgz` falls through to the hosted-git shorthand parser and npm tries to clone `github.com/artifacts/<name>.tgz`. Verified on npm 10.9.8, 11.19.1 and 12.0.2: the bare form exits 128, the `./` form resolves the tarball. `find ./artifacts` is what keeps the prefix.
- The publish step skips when the version is already on the registry instead of failing. The tag-vs-package.json guard already makes a mismatched tag impossible, so the only way to reach publish with a published version is replaying the same tag, which is either the bootstrap handover or a re-run of a failed job. Failing there would cost the GitHub release, which is the part still worth producing.

## Runtime

- `tools.ts` imports `randomUUID` from `node:crypto` like `utils.ts` does, rather than reaching for the `crypto` global. The global is only exposed unflagged from Node 19, so `logicalCallId` generation threw `ReferenceError: crypto is not defined` on Node 18 while `engines.node` promised `>=18`. One file was using a different source for the same primitive than the rest of the SDK.
- CI gates Node 20, 22 and 24, not the declared `>=18` floor. Node 18 has been end of life since April 2025 and, with the import above fixed, it passes every test except one benchmarks HTTP case that lands at 5027ms against vitest's 5000ms default. The floor is left at `>=18` because the SDK does work there; gating it would mean loosening the timeout for every test to cover a runtime nobody should be on.
